# Возобновление выпуска после занятой блокировки

Этот порядок опирается на фактический postreader-отказ этапа120 и отложенный календарный health этапа121. Блокировка остаётся защитой. Успешный HTTP-ответ сайта и старая успешная квитанция сами по себе не разрешают продолжение выпуска.

При прерывании сначала сохранить фактические `current/previous` статики, указатель и профиль API, квитанцию updater и состояние своей native-службы: `ActiveState`, `SubState`, `Result`, `MainPID`, `InvocationID`, `NRestarts`, `RestartUSec`, StartLimit и bounded journal. Возврат API мог также не получить блокировку; нельзя объявлять откат выполненным по одному намерению его вызвать.

У PostgreSQL остаются4 запуска за2 часа и штатный15min backoff. Во время отказа/автоповтора не выполнять start/restart/reset-failed/stop и не менять лимиты. `observe_start_budget` читает только точную собственную службу и ограниченный журнал; при `Result!=success` или ненулевом `MainPID` он закрывает вход. Положительный allowance не резервирует запуск. Перед действием требуется новое наблюдение, а не повтор старого результата.

После естественного завершения native-повтора проверить отдельно:

- Служба действительно не работает и завершилась успешно; журнал соответствует её invocation. Наличие `NRestarts` не заменяет результат и квитанцию.
- `latest-attempt` и `latest-success` защищают один точный snapshot/fingerprint/dataDigest. Последняя попытка имеет статус `verified`, а не `failed` или `external-copy-created-restore-pending`.
- Профиль, реальный API-reader, payload и квитанции относятся к одному `sourceSha256`; archive/previousArchive совпадают с требуемым выпуском. Старая копия читателя после отката не является копией нового кандидата.
- Полная independent-recovery proof, сроки сравнения данных и восстановления проходят существующий `assess_account_health`. Само чтение этой функции не выполняет restore и не обновляет его дату.
- Статическая транзакция терминальна. `ensure_idle` отвергает незавершённый updater и требует явного recover. До этого обычную установку не продолжать.

Если API уже новый и защищён точной независимой копией, а статика осталась прежней, продолжать конкретный подготовленный статический updater после проверки его expected-current, immutable-артефакта, ресурсов, соседей и существующих общей/собственной блокировок. Повторный запуск PostgreSQL или переключение уже установленного API ради этого не нужны. Рецепт `tmp/resume-publication-120.py` относится только к зафиксированным указателям120; перенос его на другой выпуск требует проверки реальных значений, а не замены номера в тексте.

Для занятого worker-lock внешний health CLI возвращает75 и JSON `success=false,status=deferred`. Он сохраняет прежний `health.json`: этот файл может принадлежать параллельному владельцу и не доказывает успех новой попытки. Для отложенного backup/restore также сохраняется подготовленный pending snapshot. Ошибка чтения/проверки данных имеет другой статус: она должна быть видна как failure, а не stale green.

Календарный invocation и плановый ручной postrelease-health учитывать отдельно по времени, ID и точным полным квитанциям. В121 календарный00:01:07 дал `operation-lock-busy`/TEMPFAIL75, затем плановый ручной00:01:13 прошёл. Ручной успех не исправляет исторический результат календарной попытки. Не запускать дополнительный health только ради зелёного статуса; соблюдать8/2h. Следующее время таймера остаётся прогнозом до чтения фактического журнала.

Постоянная регрессия: `node --preserve-symlinks --preserve-symlinks-main --test tests/release-interruption.test.cjs` проверяет12 переносимых Python-сценариев. Полный `python -B tests/release_interruption_test.py` на Linux добавляет2 настоящих flock-сценария. На Windows использовать `--portable`. Тесты вызывают исполняемые бюджет/health/lock-функции, подменяют внешние операции и используют только временные данные. Они не являются новым PostgreSQL/S3 restore, запуском systemd или испытанием всего coordinator.

Linux122 использовал точные модули опубликованного sourcecut91, затем их хеши независимо сопоставлены с установленными S3/base-backup/static-updater guard-модулями. Отдельный network namespace был проверен; host network и production-службы не изменялись. Новые тесты122 не входят в прежний неизменный архив91.

Основания: [Python fcntl.flock и LOCK_NB](https://docs.python.org/3/library/fcntl.html#fcntl.flock), [systemd.service RestartSec](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#RestartSec=), [отчёт122](reports/melodiajest-operations-2026-11-12-122.md), [исторический отказ120](qa/melodiajest-2026-11-11-120-native-lock-failure.json), [отложенный calendar121](qa/melodiajest-2026-11-11-121-calendar91-deferred.json).
