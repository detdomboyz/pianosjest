## Текущая архитектура

MelodiaJest использует файловый public release и отдельный native Node API. Nginx и PostgreSQL — проверенные общие upstream-образы, не собственные многослойные сборки приложения. Их теги и общие diffID не считать независимыми физическими копиями. Не переносить число слоёв и границы основы Libreta на этот проект.

В каждом независимом компоненте хранить current и проверенный previous: public release, API release, установленные updater/backup/S3/account-инструменты. Точная матрица определяется действующими указателями, ExecStart, конфигурацией и квитанциями. Разные компоненты не обязаны иметь один номер версии. Завершённый исторический отчёт не является активной задачей, однако нужные ему артефакты сначала архивируются с картой восстановления.

Исполняемый файл внутри toolkit защищает **весь** toolkit, включая sibling JSON/pins и импортируемые модули. Для исполняемого stage действует тот же принцип. Путь `retainedArchive` из текущего `update-state.json` проверяется полным SHA-256 и сохраняется; current/previous пакеты в `ops/artifacts` также сохраняются. Проверка одного работающего контейнера недостаточна: нужно импортировать фактический модуль, указанный в unit, и сверить его pins/генерируемую конфигурацию. Пакет старта PostgreSQL может иметь историческое имя `account-*` и быть отдельным действующим потребителем, отличным от текущего account-backup SDK.

Дополнительный кандидат имеет срок до конца его проверки. Обязательные исходные архивы Node/зависимостей/образа, профиль восстановления, миграционный baseline, начальные source snapshots и закреплённый источник работающего S3-протокола — отдельные входы восстановления. Их не снимать только ради числа «два». У каждого исключения фиксировать потребителя и условие снятия после проверенной замены. Retention PostgreSQL, SQLite и внешних резервных копий сохранять независимо от build retention.

## Ручное снятие старых файлов

1. Проверить HTTPS/версию, current/previous, включённые units/timers, незавершённые операции, процессы, Docker mounts, нужные профилю архивы, состояние копий и соседние приложения. Снять карту логических и выделенных байтов с учётом inode/hardlink. Секреты не выводить.
2. Сохранить `plan.json` в приватной папке D:. Каждый путь обязан принадлежать allowlist MelodiaJest; данные, активные зависимости, текущая и предыдущая версии исключаются. Новый `deploy/shared-host/host_storage.py` повторно сверяет управляющие файлы, определения units, mounts и работающие пути перед перемещением/снятием.
3. `tools/host-storage-maintenance.py manifest/export/readback` передаёт GNU-tar архив непосредственно через строгий SSH на D:, без большого файла на C: или VPS. Проверяются все архивные байты, каждый member, размер, SHA-256 и метаданные. Архивирование сохраняет числовые UID/GID, modes, symlink/hardlink, ACL/xattrs и время. Архив не перепаковывать под прежним SHA.
4. `restore` передаёт копию **с D:** в отдельный пустой Linux-каталог, сверяет все файлы/метаданные/внутренние hardlinks и сохраняет `restore-map.json`. Учитывать выделенные блоки, каталоги, рабочий комплект и минимум 2 GiB свободного запаса на пике; при недостатке места уменьшить отдельную явно описанную партию или отложить операцию. Не обходить ограничения автоматической ротации циклом.

   При измеренных повторениях допустим `pack-content` → `restore-content`: отдельный проверенный транспорт передаёт каждое SHA-содержимое один раз, сохраняя исходный GNU-tar архив на D:. Восстановление создаёт отдельные inode для исходно разных файлов, а hardlink объединяет только по исходной карте inode; UID/GID, modes, xattrs, symlinks и времена сверяются по полному исходному манифесту. Экономию передачи не выдавать за освобождённые байты. Разовый restore worker ограничен transient scope 640 MiB / 65% CPU / 32 tasks; адресное пространство Python — 768 MiB, минимум свободного диска — 2 GiB. Scope не является расписанием и удаляется после завершения.
5. Отдельно выполнить реальные сценарии восстановления приложения и данных с копии, если снимаются их recovery inputs. Для PostgreSQL использовать isolated restore без production-томов и сети, с проверкой digest, входа, владельца и новых записей двух одноразовых пользователей. Файловое сравнение само по себе не доказывает работоспособность базы или авторизации. Проверенный откат статической части и API фиксировать отдельно.
6. `quarantine` использует существующие worker locks, `/run/lock/libre-deploy.lock` и собственный `operation.lock`. Это обратимое перемещение точных immutable members. Журнал намерений записывается атомарно до первого rename; незавершённый перенос восстанавливается по presence исходника и карантина. Проверить сервис и штатные protection inputs после перемещения.
7. Только после подтверждения D-копии и реального Linux-восстановления выполнить `commit`: сверить исходное состояние, весь карантин и удалить только перечисленные файлы/пустые каталоги. Никаких Docker prune, force или удаления слоёв. При частичном отказе удаления сохранить журнал и оставшиеся members для сверки/завершения; не объявлять откат уже удалённых файлов возможным без D-архива.
8. Измерить доступные байты непосредственно до/после и собственные выделенные блоки. На общем VPS изменение свободного места также зависит от соседних процессов; отдельно показывать точное уменьшение своего дерева. Проверить адреса, background units, указатели, hashes, сети, mounts и Caddy. Убрать собственные проверенные restore scratch и промежуточные материалы.

Клиент запускается с приватным `--run D:\...` и существующим строгим `--ssh-helper` этой установки. Он не создаёт расписаний, не публикует приложение и не устанавливает зависимости. `archiveOnly`-снимок необходимой защиты не может служить разрешением удалить защищённые пути.

## Ресурсы будущих изменений

- По умолчанию одна тяжёлая сборка/проверка/распаковка на ресурс; публикации и переключения последовательно. Разрешённое параллельное чтение явно учитывать по RAM/CPU/IO; существующие ограничения сервисов и start limits не сбрасывать и не увеличивать ради ускорения.
- До выпуска записать исходный размер/пик диска, RAM и CPU для изменённого пути. Если код не влияет на ресурсы, достаточно обоснования; при влиянии нужен замер одинакового сценария до/после. Ухудшение качества, урезание runtime/моделей или данных не считать оптимизацией.
- Локальный build cache: целевой предел 2 GiB на вид; временная проверка может превышать его при записанной причине и уборке после завершения. Убирать только воспроизводимые старые записи без активных процессов. Не удалять ещё не опубликованную разработку ради лимита кэша.
- Собственные новые контейнеры задают ротацию логов явно; штатные limits RAM/CPU/pids сохраняются. Уже работающие контейнеры не пересоздавать попутно только ради форматирования compose: фактическую конфигурацию/размер журнала и потребность изменения фиксировать в отчёте. Глобальные journald/Docker настройки не менять.
- После задачи сохранять результат и точку продолжения, убирать промежуточные сборки и распаковки после проверки независимой копии. Не оставлять накопление старого runtime в нижних слоях собственного будущего образа: чистая проверенная основа, полный закреплённый runtime, один актуальный набор зависимостей и точный код.

Документация/maintenance исходники проходят применимые проверки и отдельный commit/push в main. Они не дают разрешения публиковать новые уроки или возобновлять остановленные автоматизации.
