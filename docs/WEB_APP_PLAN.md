## Исходный статический этап и сохранённый локальный режим

В v23.5.0 добавлена отдельная статическая браузерная сборка: `npm run build:web` → `dist/web`, просмотр — `npm run preview:web` или `START-WEB.cmd`. В неё входят только 18 разрешённых HTML/JS/CSS-файлов и манифест с хешами; личный каталог, INI, PowerShell и Node-сервер не копируются. В веб-режиме не выполняются запросы к локальным API и Windows-мосту. Правки сохраняются в текущем браузере, при ошибке хранилища приложение явно предлагает экспорт. Это локальный веб-релиз, не облачный аккаунт и не опубликованный домен. При переходе на другой адрес каталог нот переносится через «Перенос каталога» → «Скачать JSON» / «Открыть копию JSON». Прогресс и настройки остаются на исходном устройстве; их отдельный перенос пока не реализован.

Представление описания выделено в `piano-learning-ui.js` и имеет `.d.ts`-контракт. Это подготовка границы компонента, а не завершённый перенос в TypeScript/React. Музыкальное ядро и существующий локальный запуск не требуют установки зависимостей.

Необязательное `learning.sameGoalAs` связывает сохранённый вариант повторения с ID основного учебного разбора. При переносе оболочки сохранять эту связь в каталоге, но не объединять ID, музыкальные версии или прогресс двух записей. Проверка покрытия обнаруживает отсутствующие цели и циклы, считает только верхнюю границу числа групп; это не доказательство самостоятельности всех оставшихся целей. В памяти связанные подсказки отсутствуют в DOM, полный разбор остаётся отложенным.

Интерфейс уже работает в браузере: `index.html`, Web Audio, Web MIDI, редактор, импорт, ритм и воспроизведение. Однако `server.cjs` слушает только `127.0.0.1`, а `/api/content` читает и целиком заменяет один общий `trainer-content.json`. Это локальное приложение одного пользователя, без аккаунтов, владения черновиками, публикации и лайков.

Текущий портал в `libre/package.json` использует Next 15.5.27 / React 19.3.0 на момент чтения 5 ноября; это снимок исходников, не проверка действующего сервера. Версии и зависимости нужно согласовать перед созданием веб-пакета. Не копировать чужие секреты или клиентский идентификатор Praicer.

Постепенное подключение компонентов предусмотрено в [официальном руководстве React](https://react.dev/learn/add-react-to-an-existing-project). [Статический экспорт Next.js](https://nextjs.org/docs/app/guides/static-exports) позволяет отделить первый браузерный выпуск от последующего серверного функционала. Выбор этих этапов — проектное решение, а не требование авторов документации.

Шаблон будущего размещения — `deploy/Caddyfile.web.example`. Он обслуживает только каталог релиза; `server.cjs` в интернет не выставляется. Конфигурация ещё не применялась и не проверялась установленным Caddy на хосте. После выбора хоста проверить синтаксис его версией, HTTPS, ответы 404 на локальные API и отсутствие личных файлов. `root` и `file_server` описаны в [документации Caddy](https://caddyserver.com/docs/caddyfile/directives/file_server). В каталоге публичного выпуска не должно быть внешних символьных ссылок.

Кнопка `/api/midi-keyboard/launch` запускает EXE **на компьютере, где запущен Node.js**. После переноса этого сервера в интернет она запускала бы процесс на сервере, а не у посетителя. Такой маршрут нельзя переносить в публичный backend.

Нативная часть уже существует: C# WinForms-код внутри `midi-keyboard.ps1` получает MIDI через `winmm.dll` и вызывает Windows `SendInput`. Node извлекает код, собирает EXE и запускает окно. `START-MIDI-KEYBOARD.cmd` умеет открывать его отдельно. Клавиши и настройки этого приложения можно сохранить при выделении дополнения.

В `guitarjest` уже есть отдельные гриф, тюнер/аудиовход, редактор, точные времена отдельных нот и подсказки для пальцев/медиатора. Их нужно переносить через общий музыкальный документ и отдельный модуль гитары. Исходники обоих приложений сохраняются до проверки переноса. Код Libreta также содержит связь аккаунтов с Praicer; для музыкального сервиса понадобится собственный клиент в этой архитектуре. Её наличие в исходниках не подтверждает готовность подключения нового сервиса в production.

## Целевая структура

| Часть | Ответственность |
| --- | --- |
| Веб-клиент | Одна оболочка, каталог и профиль; переключаемые полноценные интерфейсы пианино и электрогитары |
| Общее музыкальное ядро | Партии, независимые события нот, карта темпа, воспроизведение, импорт и происхождение редакции; без DOM, хранения и системных вызовов |
| Модули инструментов | Отдельные планы и проверки: руки/пальцы для пианино; струны/лады, пальцы и техника для гитары |
| Серверный API | Вход через архитектуру портала, права владельца, черновики, публикации, версии, лайки, жалобы и ограничения загрузок |
| PostgreSQL | Пользователи и привязки к аккаунтам портала, произведения, партии, аранжировки, версии, планы исполнения, общие публикации и прогресс по инструментам |
| Хранилище файлов, совместимое с S3 | Исходные MIDI и другие пользовательские вложения; выдача приватных файлов после проверки прав |
| Дополнение для Windows | Отдельная добровольно установленная программа MIDI → клавиатура ПК; работает и без сайта |

Next.js + React + TypeScript соответствует направлению, записанному в `CODEX_PROMPT.md`, и устройству исходников Libreta. Переходить следует по модулям, сохраняя музыкальные тесты, форматы импорта и действующий локальный запуск. Отделение `fingering.js` — первый практический шаг для модуля пианино. Два независимых приложения в `iframe` не заменяют общее состояние и музыкальный документ. Выбор конкретных версий и хостинга делается перед реализацией; существующий локальный сервер не превращается в production простым открытием порта.

## Минимальная модель данных

| Сущность | Основные данные и ограничения |
| --- | --- |
| `users` / `account_links` | Локальный ID, отображаемое имя, проверенная привязка `(issuer, subject)` к аккаунту портала; секреты не попадают в клиент |
| `works` | Идентичность произведения и автор; разные редакции не объединяются только по совпадению названия |
| `scores` | ID, произведение, `owner_id`, название редакции, описание, доступ `private/unlisted/public`, текущая версия; по умолчанию приватно |
| `score_versions` / `score_parts` | Неизменяемый документ с отдельными партиями и событиями каждой ноты, исходный импорт и версия формата |
| `instrument_arrangements` | Инструмент, исходные партии/версия, точное представление или явная адаптация, происхождение изменённых нот |
| `performance_plans` | Инструмент, версия аранжировки и алгоритма, настройки, назначения, ограничения, альтернативы и статус проверки; пианистические и гитарные пальцы имеют разные схемы |
| `likes` | Уникальная пара `(user_id, score_id)`; повторный запрос не создаёт второй лайк |
| `progress` | Пользователь, версия урока, партия, аранжировка и инструмент; отдельные результаты/темп, видны только владельцу |
| `uploads` | Владелец, непрозрачный ключ файла, размер, тип, статус обработки и связь с произведением |

Для полноценной нотной модели каждой ноте нужны собственные ID, высота, начало и окончание, голос/партия и необязательное назначение руки. Не хранить произвольные ноты только как QWERTY-строку: раскладка остаётся способом ввода и отображения. При миграции исходная строка, ритм и пользовательские настройки сохраняются.

Назначения рук/пальцев, струн/ладов и исполнительских приёмов относятся к плану конкретного инструмента. Общая высота — звучащая, а записанная высота и табулатура рассчитываются представлением. Лайк и страница одной публикации общие для её инструментов; успешная тренировка, наоборот, не переносит зачёт с пианино на гитару.

## Этапы и критерии завершения

1. **Музыкальное ядро и адаптеры двух проектов.** Сохранить ноты, времена, партии, исходники и ручные назначения; выделить независимые модули инструментов. Закрыть вопросы из `FINGERING_AUDIT.md` и отдельно проверить гитарную аппликатуру.
2. **Объединённый тренажёр.** Одна мелодия открывается на пианино и гитаре; интерфейс и подсказки меняются, музыкальная позиция и повтор сохраняются. Проверить диапазоны, удержание нот, настройки устройств и раздельные результаты. Исправить узкие экраны.
3. **Портал и личные черновики.** Подключить сервис к существующей архитектуре аккаунтов отдельным клиентом, добавить серверное сохранение с проверкой владельца, резервное копирование и экспорт. Проверить реальное создание/чтение/редактирование/удаление в тестовой БД и запрет доступа пользователя A к данным B. Вход не должен быть условием знакомства с тренажёром.
4. **Публикации и лайки.** Явная кнопка «Опубликовать», публичные версии, профиль автора, один каталог с доступными инструментами и один лайк на публикацию. Проверить повторные/одновременные запросы, смену инструмента, снятие публикации и приватные черновики. Предусмотреть происхождение материалов, условия публикации и жалобы.
5. **Скачиваемое дополнение.** Выделить нынешний C# код, собрать готовый EXE/установщик, добавить подпись и версию, зарегистрировать протокол запуска, сохранить настройки при обновлении и проверить удаление установки. При первом выпуске не требовать от пользователя Node.js или локальной компиляции.
6. **Совместная работа сайта и дополнения.** Только если нужна передача MIDI обратно в веб-тренажёр: отдельный протокол сопряжения с короткоживущей сессией. Проверить эксклюзивный MIDI-порт, отсутствие двойных нот, отключение устройства и освобождение зажатых модификаторов.

На каждом этапе сохраняется работоспособная версия. Полный перенос интерфейса и соцсеть не должны блокировать исправления музыкального ядра.

## Как скачиваемая функция действительно запускается с сайта

Рекомендуемый первый вариант — установщик и собственный URI, например `pbt-companion://open?mode=midi-keyboard`.

Здесь `pbt-companion` — рабочий пример, не выбранное название общего сервиса и не уже зарегистрированный протокол. Окончательное имя согласуется с брендом после его выбора.

1. На сайте есть «Скачать дополнение для Windows» и «Открыть дополнение».
2. Пользователь устанавливает программу. Установщик регистрирует обработчик протокола у текущего пользователя.
3. Нажатие «Открыть дополнение» передаёт URI операционной системе. Браузер может попросить подтвердить открытие приложения.
4. Дополнение показывает окно, пользователь выбирает MIDI-устройство и включает режим печати. Запуск окна сам по себе не должен включать отправку системных клавиш.
5. Если дополнение отсутствует или браузер отказал, сайт предлагает установку и обычный запуск из меню Windows. Нельзя обещать надёжное скрытое определение установленной программы во всех браузерах.

**Просто скачать файл недостаточно**: его нужно установить либо один раз явно запустить и зарегистрировать обработчик. После этого открытие кнопкой сайта технически возможно. Регистрация URI и ограничения её использования описаны в [Microsoft: Handle URI activation](https://learn.microsoft.com/en-us/windows/apps/develop/launch/handle-uri-activation).

Для первого выпуска этому запуску не нужен доступ сайта к локальному HTTP-серверу. Не требуется передавать командную строку, путь к EXE, текст для печати, произвольный URL моста или постоянный токен в URI. Разрешены только заранее перечисленные действия, например открытие окна.

Любой сайт может вызвать зарегистрированную URI-схему; сама схема не подтверждает личность вызывающего. Если позже понадобится связь с веб-тренажёром, дополнение отдельно подтверждает сопряжение, связывает сессию с разрешённым origin и проверяет срок/одноразовость токена. Системные нажатия формируются только локально из MIDI и выбранной пользователем раскладки, а не по сетевой команде `send-key`.

## Возможности и ограничения браузеров

- Для обычной тренировки USB-MIDI может подключаться прямо к сайту через [Web MIDI API](https://developer.mozilla.org/en-US/docs/Web/API/Web_MIDI_API): нужен защищённый контекст и разрешение; поддержка различается между браузерами. До тестирования нельзя обещать одинаковую работу на Windows, macOS и телефонах.
- Web Audio и локальный импорт можно сохранить в клиенте. Распознавание аудио остаётся черновиком; наличие аудио не доказывает точность распознанных нот или пальцев.
- PWA удобна для установки веб-интерфейса и офлайн-кэша, но не даёт ей право вызывать Windows `SendInput` в других программах. Для этой возможности нужна нативная часть.
- Не следует строить первый релиз на предположении, что HTTPS-сайт беспрепятственно обращается к `http://127.0.0.1`. У браузеров есть ограничения смешанного содержимого, CORS и локальной сети. В частности, [Chrome документирует разрешение Local Network Access](https://developer.chrome.com/blog/local-network-access). Такой мост требует отдельного прототипа и проверки в поддерживаемых браузерах.
- Нативная функция сейчас Windows-only. Версии для macOS/Linux — отдельная реализация и отдельная проверка разрешений и системного ввода.

## Что считать готовым первым публичным выпуском

Посетитель открывает один сервис из портала, выбирает произведение и партию, переключает пианино/электрогитару и получает удобный для инструмента интерфейс и проверенные в заявленных пределах подсказки. Он может войти через аккаунт портала, добавить MIDI или поддерживаемую запись нот, сохранить приватный черновик, явно опубликовать редакцию и поставить один лайк чужой публикации.
