# Доступ MelodiaJest к существующему S3

Уточнение пользователя после фазы 16: найти файл, которым Libreta обращается к хранилищу, и работать тем же серверным способом. Фаза 18 подтвердила `/opt/libre/deploy/vps/.env.backup`, 0600: серверный ключ отличается от клиентского, List собственного `melodiajest/backups/v1/` успешен (200, MaxKeys=1, пусто). Доступ владельца нужен для изменения/чтения политики, а не как обязательное условие разрешённых объектных операций. Четыре правила ниже остаются неприменённым проектом; [текущий способ](MELODIAJEST_S3_BACKUP_RUNBOOK.md) использует серверный файл и собственные repo/password, не меняя общую policy. Независимое восстановление подтверждается отдельной квитанцией, а не результатом List.

Подготовлено 7 ноября 2026 года, эксплуатационная фаза 16. Новый бакет не требуется. Кандидат для зашифрованных резервов — `https://s3.ru-3.storage.selcloud.ru`, регион `ru-3`, существующий `libreta-backups-a7f39c`, отдельный префикс `melodiajest/backups/v1`. Рабочие объекты Libreta и резервы Praicer остаются в своих подтверждённых местах. [Топология](reports/melodiajest-s3-topology-2026-11-07.md).

## Результат диагностики

Известные четыре пути собственного защищённого конфига на VPS отсутствуют; это не поиск по всему серверу. Существующий серверный backup-ключ Libreta отличается от ключа приложения. Он использован только в памяти VPS для одного запроса `GetBucketPolicy` через уже установленный официальный `@aws-sdk/client-s3`, в отдельном ограниченном контейнере без production-mounts и запуска приложения.

В 04:56:15 UTC запрос вернул **403 AccessDenied**, одна попытка. Политика не получена, её снимок не создан. Запросов LIST, чтения и записи объектов — 0; политик не изменено, ключ не перенесён в worker MelodiaJest. Отказ относится к метаданным политики и **не доказывает** отказ объектных операций, неуспех backup Libreta или наличие/отсутствие самой политики. Стоимость запроса провайдера неизвестна.

Следующий доступ требует владельца или пользователя с подходящими правами управления политикой. Согласно Selectel, роль проверяется до bucket policy; ограниченная `s3.bucket.user` предназначена для доступа по правилам определённого бакета. Политиками управляют владелец и подходящий `member`. [Ролевая модель](https://docs.selectel.ru/s3/about/manage-access/), [bucket policy](https://docs.selectel.ru/s3/buckets/bucket-policy/about-bucket-policy/) — проверено 7 ноября 2026.

## Проверяемый проект четырёх правил

`deploy/shared-host/backup_s3_access.py` работает только с локальными байтами. Он не содержит клиента S3, секретов, создания пользователей, применения политик или сетевых запросов. [Шаблон для просмотра](../deploy/shared-host/backup-s3-access-review.json) имеет `readyForApply: false` и явный placeholder ID сервисного пользователя; это не самостоятельная bucket policy.

| Правило | Разрешение | Граница |
| --- | --- | --- |
| Location | `s3:GetBucketLocation` | Только этот бакет, без списка всех бакетов |
| List | `s3:ListBucket` | `s3:prefix` только `melodiajest/backups/v1` или `melodiajest/backups/v1/*` |
| Objects | `GetObject`, `PutObject`, `AbortMultipartUpload`, `ListMultipartUploadParts` | Только объекты внутри собственного префикса |
| Locks | `s3:DeleteObject` | Только собственные `melodiajest/backups/v1/locks/*` |

Каждое правило требует TLS и одного точного ID отдельного сервисного пользователя. Широкие `*` в действиях/принципале, ключ вместо ID, удаление backup-данных/версий/бакета и управление политиками не предоставляются. Предлагаемая роль — `s3.bucket.user`, без `s3.admin`. Совместимость этого набора с будущим закреплённым restic-worker ещё требуется проверить на собственном репозитории; успешная работа в S3 не заявлена. Ротация потребует отдельной подготовки, права удаления данных сюда не включены.

Для подготовки предложения владелец сначала сохраняет **действующую** политику в защищённый файл вне checkout, проверяет доступы существующих сервисов и фиксирует SHA256 исходных байтов. Утилита требует этот хеш, сохраняет прежние поля, правила, условия и порядок, добавляет четыре правила и отказывается при несовпавшем хеше, повторном собственном Sid, неоднозначном JSON или превышении консервативных 20 000 байт. Проверки не моделируют итоговое разрешение: роль и существующие Deny продолжают действовать.

Пример для владельца, с настоящим ID и защищённым путём вместо обозначений:

```text
python deploy/shared-host/backup_s3_access.py --template
python deploy/shared-host/backup_s3_access.py --principal SERVICE_USER_UUID --base-policy PROTECTED_EXISTING_POLICY_JSON --expected-base-sha256 EXACT_SHA256
```

Вторая команда выдаёт **обёртку предложения**, а не применяет её. SHA `proposedPolicySha256` относится к UTF-8 `proposedPolicy`, сериализованному без пробелов с одним завершающим LF. Текущая политика недоступна и реальный пользователь не создан, поэтому конкретное объединённое предложение для production ещё не сформировано. Если политики нет, эта утилита не готовит её первое создание: в Selectel появление политики меняет допуск всех прежних пользователей, для этого нужен отдельный полный разбор существующих доступов. [Создание политики](https://docs.selectel.ru/s3/buckets/bucket-policy/create-policy/).

## Что нужно до внешней копии

Потребуется отдельный серверный ключ своего сервисного пользователя и проверенный собственный scope. Значения сохраняются только в защищённом серверном конфиге, например `/opt/melodiajest/ops/secrets/backup-s3.env`, с закрытым каталогом и режимом файла 0600. Отдельный пароль restic хранится другим защищённым файлом и имеет проверенную копию вне VPS. Такие файлы пока не созданы; ключи и пароль не передаются в чат, Git или браузер.

Пользователь запретил автоматически менять соседние бакеты и политики. Поэтому применение конкретного объединённого предложения и создание доступа к общему бакету требуют необходимого решения/доступа владельца; обычная выкладка MelodiaJest этого не требует. Повышать права существующих ключей или заменять их клиентским ключом для обхода 403 нельзя.

После предоставления доступа: закреплённый шифрующий worker → свежий комплект current/previous → запись в свой namespace → точный snapshot/квитанция → чтение и расшифрование из S3 при недоступном исходнике → все SHA/размеры → два изолированных Nginx без production-томов → независимая квитанция восстановления. Затем внешний этап добавляется в существующее собственное обслуживание без дублирования таймеров. До завершения этой последовательности `independentS3BackupVerified` и постоянное `encryptionConfigured` остаются false. [Контракт внешней копии](MELODIAJEST_EXTERNAL_BACKUP.md).

Дополнительно проверена доступная браузерная сессия: официальный `my.selectel.ru` показывает форму входа, авторизованной панели нет. Номер аккаунта/пароль не вводились. Продолжение зависит от доступа владельца через панель либо подготовленного защищённого серверного конфига; значения секретов в чат не нужны.
