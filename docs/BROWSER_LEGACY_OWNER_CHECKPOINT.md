# Снимок памяти владельца legacy-прогресса

8 ноября2026, фаза19. **Реализована изолированная оболочка над настоящим `PianoProgressStore.create`**. Существующий модуль writer и `index.html` не изменены; приложение по-прежнему создаёт прежний writer. Новый `piano-legacy-checkpoint-owner.js` отсутствует в публичном allowlist. Формат, методы и положительные/отрицательные примеры закреплены в `.d.ts` и `.typecheck.ts`; зависимости не устанавливались.

Оболочка не содержит копии reducer, правил зачёта, чтения/сохранения localStorage или получения Web Lock. `record`, `refresh`, `retry`, `snapshot`, `confirmedProgress`, `exportRecovery`, `settled` делегируются действующему владельцу. Для записи он использует прежние key `music-learning-piano-v1` и lock `melodiajest:piano-progress-v1`. Новый lock не вводился. Этот контракт не присваивает legacy-summary новый статус исполнения и не восстанавливает приложение.

`prepareCheckpoint()` синхронно читает только память собственного владельца: snapshot, confirmedProgress и полный exportRecovery с pending, baseRaw, draftRaw, generation. Нет await, storage-read, IndexedDB, сети или действия с другим владельцем. Формат `melodiajest-legacy-progress-owner-v1` хранит sourceGeneration отдельно от revision оболочки. Исходные baseRaw/draftRaw остаются точными строками, включая пробелы, одиночные UTF-16 surrogate, неизвестные поля и старые редакции. JSON-оболочка сохраняет эти строки экранированием с точным обратным JSON.parse; она не нормализует persisted key и не становится вторым reducer.

Capture отказывает `BUSY`, пока выполняется делегированный mutator, его job или onChange. В частности, синхронный вызов из storage/onChange не видит промежуточную структуру. После отказа записи и завершения job доступен снимок подтверждённой модели, ошибки и всей очереди: failed pending не принимается за успешно сохранённое. При write-success/readback-failure сохраняется неопределённость SAVE_NOT_CONFIRMED; поведение точного повтора и дедупликации остаётся у исходного writer.

Собственная revision увеличивается на входе/выходе каждого mutator и уведомления, включая ошибки и попытки без изменения данных. Прежняя sourceGeneration этого не гарантирует: например, неверный operation меняет code без смены raw. Переполнение revision закрывает checkpoint-функции, а работа прежнего writer не обрывается. Для ревизии нельзя оборачивать произвольный уже существующий owner с потерянной историей: этот factory сам создаёт и удерживает настоящий writer, не отдавая ссылку на него.

Token содержит только метаданные, принадлежит одному экземпляру и связан через WeakMap; подделанная JSON-копия или token другого owner даёт PLAN. `readCheckpoint(token)` возвращает неизменяемый приватный `{id:'legacy-progress',status:'observed',raw,generation}` для кандидата15. Ранее подготовленные значения остаются читаемыми после новых записей. `isCurrent(token)` сравнивает revision и сериализованную память этого owner, без I/O; закрытый/чужой token отвергается. `closeCheckpoint()` инвалидирует только checkpoint-токены. Принятые записи, очередь и методы исходного writer продолжают работать; закрытие не является отменой сохранения или удалением pending.

**Граница currency проверена отрицательным тестом:** другая реальная вкладка/writer может изменить storage, пока память первого owner и его token остаются прежними. `isCurrent:true` не доказывает свежесть persisted значений, отсутствие ABA, общую блокировку или право применить snapshot. До production-подключения все mutators должны идти через участвующих владельцев и согласованный барьер; обёртывание одной функции не создаёт защиты для остальных writers.

Новый component входит в прежний incomplete candidate без изменения алгоритма UTF-16/SHA256 или формата15. Даже при его наличии кандидат остаётся `completeCopy:false`, `consistency:'uncoordinated'`, с причинами WRITER_BARRIER_NOT_IMPLEMENTED и MEMORY_CONTRACTS_NOT_VALIDATED; ещё семь компонентов не подтверждены. Неполный кандидат можно записать/прочитать в изолированном store17, но это не полный backup, не облачная синхронизация и не восстановление application state. Публичный интерфейс подготовки такой копии ещё не включён.

Нативная проверка на отдельном loopback-origin использует искусственный полный каталог580/168строк прогресса, настоящий Web Locks и IndexedDB. Подтверждены idle-export без storage I/O, отказ при активной блокировке, failed pending/base/draft после повторного открытия и точный retry при сохранении прежнего исторического pending. Создана и удалена только собственная уникальная QA-база; production-ключи, база и личный каталог не читаются. [Квитанция](qa/melodiajest-2026-11-08-19-native.json).

Первичные основания: [WHATWG HTML, §8.1.7.3 Processing model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model) и [Web Locks request](https://w3c.github.io/web-locks/#api-lock-manager-request), прочитаны08.11.2026. Первое описывает задачи и microtasks одного agent; второе — кооперативную блокировку участников в storage bucket. Наша idle-граница/revision, JSON-envelope, лимит кандидата и API — решения проекта. Спецификации не утверждают атомарность нашей общей копии. Web Locks — Editor’s Draft, это явно учитывается.

Далее — контракт памяти следующего владельца whole-capture: pending/recent/jobs и контекст scope без сброса MIDI-событий. Затем оставшиеся владельцы и общий writer-barrier; выбор/экспорт кандидатов и application restore — отдельные этапы. Уроков этот этап не добавляет.
