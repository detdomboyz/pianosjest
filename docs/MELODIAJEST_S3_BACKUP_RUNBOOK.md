# Серверный S3-доступ и собственный репозиторий MelodiaJest

7 ноября 2026: зашифрованная запись и независимое восстановление подтверждены в [фазе 18](reports/melodiajest-operations-2026-11-07-18.md). В [фазе 19](reports/melodiajest-operations-2026-11-07-19.md) внешний этап подключён к существующим daily/weekly/hourly службам, реальные пути и откат проверены. [Расписание, свежесть и повтор без отправки](MELODIAJEST_S3_SCHEDULE.md). Первые native daily/weekly внешнего этапа ещё ожидаются; ротация не включена.

По уточнению пользователя используется существующий серверный способ Libreta: защищённый `/opt/libre/deploy/vps/.env.backup` → эффективное окружение Compose backup → только `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` и при наличии session token. Файл остаётся у Libreta и читается без изменения. Клиентский ключ приложения отличается и отвергается; пароль и repository Libreta не передаются restic MelodiaJest. Новый бакет не требуется.

Собственный адрес фиксирован: `s3:https://s3.ru-3.storage.selcloud.ru/libreta-backups-a7f39c/melodiajest/backups/v1`, регион `ru-3`. Отдельный пароль — `/opt/melodiajest/ops/secrets/restic-password`, root/0600; собственный конфиг без значений секретов — `/opt/melodiajest/ops/s3-backup.json`. Общий серверный ключ не стал IAM-ключом только одного префикса: runner ограничивает свои команды и адрес, а область существующих прав ключа шире этого программного ограничения и отдельно не менялась. Четыре правила из фазы 16 остаются проектом для возможного последующего перехода на отдельную узкую identity. Общие политики не редактируются.

## Runtime и секреты

`backup_s3_runtime.py` использует отдельный официальный restic **0.19.1**, бинарный SHA256 `20d4142678d0d95ec11a4759def1b73fd9190abc9ca19e4b62d067c0b387e639`; SHA256SUMS и PGP проверены по опубликованному первичному fingerprint `CF8F18F2844575973F79D4E191A6868BD3F7A907`. Бинарник закреплён в собственном tooling, существующий Python-образ резервирования используется по immutable ID, без его изменения и без запуска backup приложения Libreta. [Официальная установка/проверка](https://github.com/restic/restic/blob/v0.19.1/doc/020_installation.rst), [выпуск](https://github.com/restic/restic/releases/tag/v0.19.1).

Секреты поступают в собственный временный контейнер через stdin, а в restic — через окружение дочернего процесса внутри контейнера. В Docker Config.Env, командной строке, браузере и квитанции их значений нет. Контейнер получает только собственные mounts, read-only root, cap-drop ALL, no-new-privileges, 768 MiB RAM, 0,5 CPU и 64 PID; к `libre_public` не подключается. Команды удаления данных, prune, unlock, изменения ключей и политик не предоставлены. Кеш, временные файлы и распакованные копии закрыты root.

На компьютере сохранён отдельный зашифрованный DPAPI CurrentUser-файл в `tmp/melodiajest-private/restic-password.dpapi`. Каталог разрешён только владельцу Windows и SYSTEM, исключён Git и allowlist-архивами. Чтение/расшифрование и совпадение с серверным паролем проверены без вывода секрета. Файл **требует того же профиля/учётных данных Windows**; одна его копия не защищает от потери этого профиля. Его следует сохранять вместе с возможностью восстановления профиля. Секреты не передаются в чат. `tools/melodiajest_secret.py` предоставляет DPAPI-функции для передачи восстановленного пароля в память; команды печати пароля нет.

После потери VPS для чтения S3 нужен также действующий серверный доступ Selectel или его перевыпуск через учётную запись провайдера. AWS-секреты Libreta не включены в комплект MelodiaJest. Подтверждённое восстановление данных не является проверкой восстановления аккаунта провайдера или утраченного Windows-профиля.

## Комплект и приёмка

`backup_s3_job.py prepare` использует существующий `backup_replica.prepare`: свежие согласованные current/previous, опубликованные исходники и 12 собственных controls. Дополнительно включаются allowlist-архив текущего development checkout, собственный S3-конфиг без секретов и подписанный сжатый runtime. `payload.json` фиксирует каждый путь/размер/SHA; собственный SHA манифеста сохраняется отдельно. Пароль, AWS-ключи, `.env`, личный `trainer-content.json`, MIDI-настройки и браузерный прогресс в комплект не входят.

Первое `backup --initialize-empty` возможно после ограниченной проверки собственного префикса MaxKeys=1; существующий непустой namespace не переинициализируется. Намерение и каждый завершённый шаг сохраняются до продолжения. Успешный snapshot фиксируется полным ID. Анонимный доступ к созданному config проверяется до записи полезной нагрузки. Эти проверки не являются аудитом всех политик аккаунта.

`restore` получает пароль, расшифрованный на компьютере из независимой DPAPI-копии, через stdin. Он не читает парольный файл VPS. Исходный payload временно убирается с известного пути; контейнер получает только пустые destination/cache и runtime. Из S3 восстанавливается точный snapshot, затем проверяются все SHA/размеры и полный состав, отдельно восстанавливается development archive, а current/previous запускаются в двух Nginx без сети, публичных портов и production-томов. Только успешное завершение всей последовательности даёт `independentExternalCopyVerified: true`. Временные расшифрованные каталоги удаляются только после проверки своих абсолютных путей; исходный закрытый payload возвращается.

Ручной этап фазы 18 и интеграция фазы 19 — разные результаты. Сейчас используются post-hooks трёх существующих служб; новых таймеров/desktop heartbeat нет, Libreta не менялась. Плановые restores читают собственный серверный пароль и явно не выдаются за восстановление пароля из DPAPI-копии. Ротация остаётся отдельным этапом. Число HTTP-запросов restic и счёт провайдера неизвестны: вызовы программы не являются биллингом. Учебные файлы/S3-CDN и ускорение сайта этим резервированием не реализуются.

Лёгкая проверка читает `/opt/melodiajest/ops/external-s3/last-backup-success.json`, `last-restore-success.json`, `last-attempt.json` и отдельный каталог `scheduled`: last-success, last-check-success, last-restore-success, last-backup-attempt, last-restore-attempt, last-attempt, health. Сопоставить snapshot/manifest/coverage, возраст и последний статус. Не обходить бакет и не скачивать тот же комплект заново. Наличие старого успеха не скрывает неудачную последнюю попытку. Базовый серверный health и внешний health учитываются отдельно; существующая systemd-служба проходит только при успехе обоих шагов.
