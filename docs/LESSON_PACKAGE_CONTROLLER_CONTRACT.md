# Единый контроллер подтверждённой записи

Дополнение 8 ноября 2026: `preparePendingRestore()` → `commitPendingRestore(plan)` [возвращает поддерживаемую архивную правку](PENDING_RESTORE_CONTRACT.md) в pending через ту же очередь. Pending-restored не повышает confirmedRevision и не означает saved. Для активации остаётся отдельный явный prepareRecovery/commitRecovery; архив сохраняется. Импорт recovery-файла и подключение всех writers ещё ожидаются.

Фаза 29, 7 ноября 2026. `piano-lesson-package-controller.js` соединяет проверенные loader → shared planner → store.stage/commit/recoverPending. Модуль, типы и стенд подготовлены изолированно; публичный allowlist и приложение 23.5.46 не подключены. Он не читает localStorage, прогресс, сеть, MIDI или звук. Установка зависимостей не нужна.

`create({store, subtle, onChange})` принимает существующий store явно. Импорт и создание не открывают БД. Обработчик получает только phase/code/confirmedRevision/stagedOperationId, без личного каталога. Ошибки провайдера заменены перечисленными типизированными кодами. Ошибка наблюдателя не превращает уже завершённую запись в отказ.

`initializeV7(verified, catalog)` принимает исходный capability загрузчика и уже подготовленный JSON/v7-каталог, включая личные записи. Это начальная запись в пустой store с проверкой отсутствия current внутри транзакции. Метод не копирует и не мигрирует старые байты localStorage и сам по себе не доказывает готовность legacy-миграции. Сохранённый pin должен приходить от доверенного выпуска; SHA256 не удостоверяет автора самостоятельно.

`read()` возвращает замороженный снимок, известный этому контроллеру и store. `writeCatalog(view, catalog)` принимает только такой снимок, сохраняет его pin и копирует кандидат до первого await. Записи одного контроллера стоят в очереди. Два изменения от одного снимка не объединяются автоматически: второе отклоняется как STALE. Два настоящих соединения дают одного победителя, другой видит PENDING либо STALE по моменту гонки. Обновление старого снимка, автоматическая повторная запись и принудительное разрешение конфликта отсутствуют.

`prepareUpdate({previous, incoming})` требует исходные capability проверенного загрузчика, читает актуальный снимок и вызывает тот же planner, что используется офлайн. Асинхронные SHA256 выполняются до транзакции записи. Контроллер удерживает исходный полный снимок; поздняя правка, в том числе во время digest, делает применение устаревшим. Подделанные, клонированные и выданные другим контроллером предложения отклоняются. Блокированный planner-кандидат не попадает в store.

`commitUpdate(proposal)` создаёт один store-план на предложение и сначала сохраняет полный pending. После подтверждения stage вызывает commit. Повтор того же предложения использует тот же operationId; previous и квитанция не вращаются повторно. Общая запись каталога также проходит stage → commit. Состояние saved выставляется только после завершения commit Promise, который store разрешает по transaction.complete. Между stage и commit может остаться незавершённый черновик; его существование не означает изменения рабочей версии.

`prepareRecovery()` возвращает непрозрачный токен найденного pending и не применяет его. Только явный `commitRecovery(token)` подтверждает восстановление. Токен нельзя переносить через JSON или другой контроллер. `exportRecovery()` вызывается явно и возвращает текущий/предыдущий каталог, квитанцию и pending для сохранения пользователем. Нет автоматической выгрузки личных материалов, удаления черновика или обхода STALE/SCHEMA/PENDING. Исходные данные сохраняются для отдельного разбора.

`close()` закрывает store и запрещает новые/ещё не начатые действия. После подтверждённого stage закрытие оставляет pending. Уже начатая native-транзакция может завершиться: окончательный результат определяется Promise, закрытие не является отменой подтверждённой записи. Проверка соединения после закрытия отличается от аварии процесса/питания.

Node проверяет исполняемый модуль и явно обозначенный I/O spy без копирования алгоритма IndexedDB. Браузерный стенд `tools/qa-piano-package-controller.cjs` раздаёт только разрешённые файлы на собственном loopback-порту. Он использует настоящий loader, planner и IndexedDB: точные поля личных материалов, повтор, позднюю правку во время digest, очередь, два соединения, внедрённый QuotaExceededError после stage и явное восстановление после переоткрытия соединения. 11/11 сценариев пройдены; физическое заполнение диска, авария питания и закрытие настоящей вкладки именно с этим контроллером не проверялись. Прежняя фактическая проверка закрытия вкладки store остаётся доказательством фазы 27.

Прочитан первичный [W3C IndexedDB §2.7.1](https://w3c.github.io/IndexedDB/#transaction-lifecycle) и [§5.4](https://w3c.github.io/IndexedDB/#commit-transaction), проверено 7 ноября 2026: транзакция завершается атомарно, complete следует после записи; исключение последующего observer не отменяет commit. Strict — запрос браузеру, не обещание защиты от любых физических отказов. Очередь контроллера, формат pending и коды конфликтов — решения проекта.

Следующий системный этап: отдельная подтверждённая копия исходных legacy-байтов до преобразований, ручной разбор stale/future pending и последовательный перевод каждого writer (`loadCatalog`, импорт, редакторы, удаления, порядок, аппликатура, `saveCatalog`). До проверки всех путей остаётся bundled/localStorage-режим. Прогресс и его история сохраняются отдельным контрактом; их нельзя включать в catalog-кандидат.
