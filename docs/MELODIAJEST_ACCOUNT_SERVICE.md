# Аккаунты и личная музыка MelodiaJest

Уточнение пользователя 8 ноября 2026: сейчас нужна **отдельная регистрация MelodiaJest**, в будущем аккаунты должны связываться по SSO. Это текущий приоритет продукта. Курс и его цель минимум 1000 содержательных уроков сохраняются.

Состояние на 9 ноября 2026: **23.5.64 выложена и проверена**. Отдельная регистрация, личные мелодии/публикации/настройки/предложения дополнены серверными испытаниями, XP, оценками и комментариями. Рабочая собственная БД — PostgreSQL 18.6 через Unix socket; независимое восстановление кода/Node/pg/image/данных/configs подтверждено. [Проверенный выпуск22](reports/melodiajest-operations-2026-11-08-22.md), прежняя регистрационная фаза21 сохранена как история.

Внутренний случайный ID пользователя постоянен. Парольные credentials и будущие внешние identities `(issuer, subject)` хранятся отдельно. Мелодии, настройки и предложения принадлежат внутреннему ID, поэтому новый способ входа не требует менять владельца. Будущий SSO использует явное подтверждение обеих сторон и отдельный клиент MelodiaJest; совпадения email недостаточно для объединения. SSO-маршрутов и переиспользования ключей Libreta/Praicer сейчас нет.

Первый вход — логин 4–32 латинских символа и пароль 15–128 символов, без обязательной почты. Одноразовый случайный резервный код выдаётся при регистрации/смене пароля; пользователь сохраняет его приватно. В базе только scrypt-хеш пароля с солью и хеш кода. Восстановление меняет код и отзывает прежние сессии. Письма, подтверждение email, MFA и вход через портал не объявляются готовыми.

API имеет отдельный путь `/api/service/v1/`. Проверяет владельца на сервере, точный Origin и CSRF для записи, ожидаемый аккаунт вкладки для личных запросов и версию объекта при сохранении. Сессии случайные, на сервере хранится SHA256; production cookie `__Host-melodiajest-session` использует Secure / HttpOnly / SameSite=Lax / Path=/, без Domain. Ограничения запросов сохраняются в PostgreSQL; тяжёлых операций scrypt одновременно не больше двух.

Личная мелодия сначала приватна. Публикация создаёт отдельный снимок с явным подтверждением прав; изменение черновика не обновляет его автоматически. Чужой ID не даёт чтения, редактирования, публикации или снятия публикации. Музыкальные редакции и публикации сохраняют историю. Предложения исправлений отправляются отдельно со статусом «получено» и не меняют общий курс.

Данные находятся в собственной PostgreSQL `melodiajest`, отдельном контейнере без TCP/общей сети и с отдельной ограниченной SCRAM-ролью. Внешние БД/тома не используются. Исходная SQLite с application_id `0x4d4a5331` сохранена как источник миграции; восстановление старой SQLite после допуска PostgreSQL-записей запрещено. API использует отдельный Node 24.22.2 и pg 8.23.1 в собственном веб-пакете; корневой Node 20 и локальный запуск не требуют установки зависимостей. API работает из `service/server.cjs` за Unix socket; ни он, ни локальный Windows `server.cjs` не входят в публичную раздачу. Музыкальные контракты и внутренние UUID сохранены.

`service/backup.cjs` сохранён для прежнего формата SQLite и изолированного переноса. Текущий `service/postgres_backup.py` читает согласованный pg_dump/digest, закрытый payload с Node/pg/source/full OCI image/своими конфигами, затем читает и расшифровывает S3-копию в новый кеш. Из восстановленных байтов запускаются отдельные PostgreSQL и API без production-томов. Проверяются digest, размеры/SHA256, две записи и границы владельца, неверный пароль и запрет DDL. Эксплуатационные квитанции — `ops/account-postgres-backups/latest-attempt.json` и `latest-success.json`; неуспех последней попытки нельзя скрывать старым success.

Первичные рекомендации: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Node.js Crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [Node.js SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html). Параметры scrypt N=32768, r=8, p=3 соответствуют одному из указанных OWASP сочетаний; это не заявление сертификации сервиса.

Серверный API — `melodiajest-account.service`, отдельный непривилегированный пользователь, `PrivateNetwork=yes` / `AF_UNIX`. Собственный Nginx подключается к `/run/melodiajest-account/api.sock`; публичного TCP-порта API нет. Общий Caddy и соседние базы/сервисы не менялись. Обновление backend — `service/operate.py` / `deployment.py`, без миграции или отката рабочей БД. Неизменный локальный `npm start` использует прежний Node 20; `START-WEB.cmd` собирает автономный браузерный вариант через `build:web:offline`. Публичный `build:web` включает аккаунты.

Ежедневная копия аккаунтов — существующий `melodiajest-account-backup.timer` (02:10 UTC плюс случайные 0–5 минут). PostgreSQL-ветка проверена настоящим ручным systemd-запуском; её календарный запуск ещё не наблюдался. PrivateNetwork/AF_UNIX host-службы сохранены, сетевые пробы и S3 выполняются через отдельные ограниченные контейнеры. Неизменный логический digest/код/controls повторно использует подтверждённую копию не более семи дней; целевая свежесть — 30 часов, интеграция её чтения в hourly health ещё предстоит. Локально сохраняются три проверенных payload, image hard-links не выдаются за независимость; внешнее удаление не настроено. Стоимость запросов полностью не измерена и не считается нулевой.

Новые серверные испытания, зачёт, лучшие результаты, XP, оценки и комментарии сохраняются в PostgreSQL по владельцу и музыкальной редакции. **Прежняя** история попыток/подготовок остаётся отдельно в браузере по ID аккаунта; серверные копии её не покрывают. Прежние анонимные ключи/редакции не удалялись и автоматически не отправляются в новый аккаунт. Явный перенос старых данных требует отдельного контракта владельца/версий/writers. Старые изолированные checkpoint-прототипы в production не активированы.

Ограничения первого выпуска: email-восстановление/MFA/SSO и кабинет модератора — следующие этапы. Предложения сохраняются приватно со статусом «получено». Лимиты: 25 MiB на аккаунт, 200 личных мелодий, 1000 регистраций сервиса; их изменение требует измерения ресурсов. Будущий SSO добавляется собственным клиентом и явной связью `(issuer, subject)` с сохранением внутреннего UUID; пароли и ключи соседних сервисов не копируются.
