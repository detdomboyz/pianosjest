# Внешнее обслуживание в существующих службах

Фаза 19, 7 ноября 2026. Установлено в три существующие службы; реальные service paths, повтор без S3-запросов и откат проверены. 734 npm-теста прошли. Первые нативные daily/weekly запуски внешнего этапа ещё ожидаются; первый hourly до завершения bootstrap отметил отсутствие квитанций, затем ручной запуск health прошёл. [Доказательства и ограничения](reports/melodiajest-operations-2026-11-07-19.md).

`backup_s3_schedule.py` добавляется через собственные `20-external-s3.conf` в три существующие службы: melodiajest-backup, melodiajest-restore-check, melodiajest-backup-health. Их базовые файлы, три таймера и расписания сохраняются. ExecStartPost выполняется после успешного основного шага; его ошибка делает службу неуспешной и сохраняется в собственной квитанции. [Правила systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecStartPre=).

Ограничения PrivateNetwork, AF_UNIX, ProtectSystem=strict, ReadWritePaths и MemoryMax сохраняются. Сеть доступна только ограниченным временным Docker-контейнерам; anonymous config probe перенесён туда из сетевого пространства хоста. Во временной systemd-службе проверены разрешение серверных backup-credentials и 403 собственного anonymous GET; значения ключей не выводились.

У daily-шага есть устойчивая версия покрытия: current/previous web/source SHA, собственные controls, development archive, scheduler controls и runtime. Случайный ID/время очередного серверного snapshot не создают новую полезную нагрузку. При совпадении сохранённого покрытия и успешного restore повторной отправки нет; обновляется отдельная локальная проверка покрытия, а время настоящей записи и удалённого восстановления сохраняется. Раз в неделю тот же точный snapshot заново читается из S3 с пустым кешем и проверяется в изоляции.

Новый комплект: prepare → backup → cold restore → успешная общая квитанция. Если restore не прошёл, backup остаётся созданной копией без нового подтверждения независимого восстановления; следующая попытка продолжает тот же snapshot. Ошибка последнего restore не скрывается старым успехом или обычным unchanged-пропуском. У backup/restore есть отдельные last-attempt; health учитывает их, текущий fingerprint, точный snapshot/manifest, локальную проверку моложе 30 часов и S3-restore моложе 8 дней. Локальная проверка не обновляет возраст S3-restore. Health не делает запросов к бакету.

Scheduler конфиг `/opt/melodiajest/ops/s3-schedule.json`, root/0600, отделён от transport-конфига `/opt/melodiajest/ops/s3-backup.json`. Transport v2 больше не содержит поля scheduledExternalBackup; старый v1 с false читается для восстановления фазы 18. Фактическое расписание определяется наличием/составом drop-ins и квитанциями systemd, а не транспортным JSON.

Внешний payload дополнен schedule-controls.json: allowlist из 20 файлов собственных инструментов, конфигов без секретов и трёх drop-ins, каждый с размером/SHA. При cold restore они записываются и перечитываются в новом каталоге; в production не устанавливаются. Пароли, .env, AWS-значения и чужие unit-файлы не включаются. После нового публичного выпуска scheduler берёт его проверенные исходники из серверного snapshot, если development checkpoint относится к прежней версии.

Плановое восстановление использует собственный root/0600 пароль и честно отмечает passwordReadFromVpsFile=true, passwordRecoveredFromIndependentCopy=false. Независимое восстановление пароля с компьютера подтверждено отдельно в фазе 18; DPAPI требует сохранённого Windows-профиля. Копии данных считаются прочитанными из S3 только после действительного восстановления. Браузерный прогресс не покрывается.

Установщик `tools/install-melodiajest-s3-schedule.py` принимает проверенные stage/source receipts и режим install/rollback; `--rollback-installation` выбирает прежний собственный каталог по точному имени. Он сверяет локальные/серверные SHA, сохраняет baseline, восстанавливает его байты в изоляции, проверяет systemd и прежние ограничения. Реальный цикл install → rollback → install прошёл. При откате сверяются SHA установленных файлов и baseline; удаляются только отсутствовавшие до установки собственные файлы из фиксированного набора шести путей. Базовые шесть unit-файлов и таймеры сохраняются.

Политики/чужие объекты не меняются, автоматического init непустого namespace, prune/forget/unlock и ротации нет. Существующий серверный ключ имеет прежнюю IAM-область; префикс фиксирует программа. Число HTTP-запросов restic и счёт провайдера остаются неизвестны. Все серверные изменения проходят фактическую общую и собственную блокировки. Службы Libreta/Praicer не перезапускаются.
