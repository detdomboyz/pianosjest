# Отдельное сохранение неполного кандидата

Фаза17, 8 ноября2026. `piano-browser-checkpoint-store.js` и `.d.ts` реализуют изолированное append-only хранилище. Они не подключены к публичной сборке, действующим writers или личным данным пользователя. Вход — приватный DTO из `piano-browser-checkpoint-candidate.readCandidate(token)`, а не его метаданные/token. Применения к приложению, восстановления прогресса, удаления, ротации и сетевых операций нет.

## Проверка до записи

Все примитивы DTO фиксируются синхронно до первого digest. Проверяются точные поля, обычные объекты/массивы без accessors, символов и пропусков; семь persisted-ключей и восемь компонентов в порядке контракта; причины unavailable, поколения, счётчики и ограничения. Неизвестная версия или дополнительные поля отвергаются без открытия БД. Строки не разбираются как пользовательский JSON и не нормализуются: null, пустое значение, буквальный `null`, повреждённая строка, NUL и одиночные UTF-16 code units остаются различными.

Хеши, счётчики, причины и общий ID пересчитываются через настоящий candidate-builder и его протокол presence byte + UTF-16LE. Второй копии алгоритма хеширования нет. Ошибка проверки не превращается в пустой кандидат.

## Собственная БД и подтверждение

Фиксированная БД `melodiajest-browser-checkpoints-v1`, версия1, один store `candidates`; для изолированных проб разрешён только суффикс `-qa-…`. Конструктор ничего не открывает. При создании новой БД добавляется только свой store. Неизвестная схема, keyPath, autoIncrement, индексы или более новая версия дают ошибку без сброса/удаления. При versionchange соединение закрывается, прежние записи не мигрируются.

`save(candidate)` сначала полностью проверяет DTO, затем в одной readwrite-транзакции проверяет известный ID и число собственных записей. Не более четырёх различных кандидатов; при заполнении новый отклоняется, предыдущие не удаляются. Идентичный контент переиспользует исходную запись с первоначальными capturedAt/storedAt; новая дата наблюдения не создаёт дополнительный слот. Индекс времени, перебор чужих хранилищ и автоматический current-pointer не реализованы.

Запрос добавления недостаточен для успеха: метод ждёт `transaction.complete`, открывает отдельную readonly-транзакцию и заново проверяет все данные/хеши. В чтении используются get и getKey для одного ID: существующий ключ с undefined считается повреждением, а не отсутствием. `read(id)` явно возвращает приватный проверенный кандидат, либо null при действительно отсутствующем ключе. Для чтения после нового открытия вызывающая сторона должна сохранить известный ID из квитанции; интерфейс выбора/экспорта ещё не реализован.

Квитанция содержит только метаданные: `stored-incomplete`, `completeCopy:false`, `consistency:uncoordinated`, счётчики/причины, saved/reused/read и readbackVerified. Raw-строки в квитанции отсутствуют. `strict` запрашивается у native-транзакции, фактически наблюдённый durability отражается отдельно; при неизвестном значении не утверждается strict. Это подсказка браузеру, не обещание защиты от любого сбоя ОС, удаления origin или вытеснения данных. Persistence permission не запрашивается.

Quota/abort отклоняют транзакцию и сохраняют прежние записи. Если транзакция уже завершилась, а новое чтение не удалось, возвращается `UNCONFIRMED` с `writeMayHaveCommitted` и безопасным reasonCode: такое состояние не называется гарантированным отказом записи. Следующее действие — отдельное чтение известного ID. Повреждённый существующий кандидат не перезаписывается при повторной попытке.

Это не перезапуск браузера/ОС и не восстановление работающего приложения.

## Первичные основания

- [W3C Indexed Database API3.0](https://w3c.github.io/IndexedDB/), Editor’s Draft30.10.2026, §2.7.1/§4.10: завершение транзакции отличать от успеха одного запроса. §4.4: scope/режим транзакции, versionchange и схема. Durability strict — подсказка браузеру. Перечитано08.11.2026.
- [WHATWG Storage](https://storage.spec.whatwg.org/), §4.5 и§7.1: режим best-effort и действия при давлении на хранилище. Существование записи не доказывает независимую резервную копию. Перечитано08.11.2026.

Схема БД, лимит4, DTO, хеширование, incomplete-статусы и ошибки — решения проекта; стандарты не утверждают данный контракт.
