## Два появления одной высоты

| Ожидаемый локальный ID69 | MIDI | Аннотация руки/пальца | Доли | Номер появления65 |
| --- | --- | --- | --- | --- |
| ascent-0-1 | 65/F4 | правая/1 | 0–1 | 0 |
| ascent-7-0 | 65/F4 | левая/1 | 7–8 | 1 |

Это два различных ожидаемых события, не две ссылки на один сыгранный звук. ID пока символические внутри документа, не сохранённые app noteID. Физическая рука/палец аннотированы в плане и не определяются MIDI. Между этими F4 нет legato-связи: первая связана в верхней линии с G4, последняя — в нижней с E4. Номер появления той же высоты нужен сопоставлению, а не превращает высотную очередь в музыкальный голос.

## Реальный путь данных

`index.html:selectMidiInput` читает выбранный живой input, маскирует статус через0xf0 и оставляет noteOn/noteOff; номер MIDI-канала/порт/velocity в запись попытки не попадают. NoteOn velocity0 обрабатывается этим кодом как Off. `handleNoteOn/Off` записывает type/midi/performance.now/source; повторный активный NoteOn браузер не добавляет в attemptEvents. Это именно путь живой попытки, а не отдельный MIDI-file importer.

`learning-client.js:submit` переводит timestamps к captureOrigin и отправляет type/midi/at/source, observedUntil и observationInterrupted. Отпускания получают defaultsource:midi, ручные NoteOn остаются keyboard и не проходят MIDI-зачёт. `eventsInput` сервера проверяет точные4поля, диапазон/монотонность/границы; физическая рука и ожидаемый noteID от клиента не принимаются. План и его версия берутся из saved plan_raw.

В `practice-assessment.js` active keyed bymidi формирует отдельное сыгранное появление на каждый принятый NoteOn. Повторный On без Off добавляет причину отказа и пропускается. Общая очередь каждой высоты расходуется через shift в хронологическом порядке ожидаемых шагов. Это не поиск первого совпадения отдельно для каждой руки.

В service metrics есть свой повторный разбор played/queues. При malformed повторном On он добавляет played иначе, чем core; окончательный assessment всё равно core и quality0 при отказе. Новая политика должна использовать **одну общую эфемерную таблицу сопоставления из реального core** и для связей, и для метрик. Отдельный второй оценщик или самостоятельный matcher в service не предлагается. Изменение старых диагностик/результатов задним числом не выполняется.

## Пять новых baseline-проб

Все события синтетические; source:midi выбирает реальную ветку, не обозначает устройство. Пройдена настоящая eventsInput, assessment прямого core точно равен assessment service grader во всех5случаях. Абсолютные целые ms, Off перед On при одинаковом времени. План — исходные16 нот/0–7/44BPM/legato, без добавленных timeLimit30, timingPrecisionv2 или voice-контракта; прямой grade вызван вне маршрута/аккаунта/БД/XP.

| Случай | Текущий результат |

Положительный baseline не доказывает двуручное legato: ветка по-прежнему пропускает двухнотные шаги65. Новых cases будущей политики исполнено0.

## Предлагаемая версия и область

Проектные имена: `expectedNoteLinks.version:2`, `policy:piano-voice-legato-time-disjoint-v2`, requirement `expected-note-links-v2-time-disjoint-midi`, saved `gradeContract:piano-note-links-v2-time-disjoint-midi`. Они ещё не существуют в runtime. v1 сохраняет свой disjointPitchSetsBetweenVoices=true. v2 наследует биекцию локаторов/ID, проверку MIDI/sourceBinding, две синхронные одноголосные линии, четверти/целые границы/2–32шага/до64нот и полное явное описание соседних legato/rest-переходов. Меняется только допустимость общей MIDI-высоты в разных линиях при однозначно разнесённых появлениях.

Каждое ожидаемое появление имеет собственный ID из версии музыкальных данных. Канонические шаги, midis и параллельные noteIds определяют **глобальный порядок событий по времени**, а не порядок обхода массива voices. Для каждой MIDI-высоты наблюдённые появления потребляются ровно один раз глобально; новый match должен содержать expectedNoteId→playedOccurrenceIndex. Номер сыгранного появления выводится из записи сервером и живёт только во время проверки, не является новым клиентским полем/долговременной копией сырого MIDI. Общая таблица должна поступить из core в серверные метрики новой политики; legacy API/result shape сохраняются.

Поиск `.find(midi===65)` в каждой линии, повторное использование сыгранного появления, привязка по регистру к физической руке и включение fingerprint-derived adapterID внутрь того же fingerprint недопустимы. Используется отдельная author-ID→локатор карта07. Окончательный sourceBindingSHA можно получить только из окончательных нормализованных данных будущего урока; сейчас он не выдумывается и не выдаётся за существующую музыкальную версию.

## Консервативная граница времени

Непересечение только номинальных нот недостаточно. Для соседних ожидаемых появлений одной MIDI-высоты предлагается требовать строгий зазор между **последним допускаемым отпусканием предыдущей** и **первым допускаемым вступлением следующей**. Границы берутся из той же политики, что применяет реальный assessor, при том же gradingBPM/profile; в новом коде они должны иметь общий источник, не расходящиеся копии формул.

Для нынешнего standard duration profile: O=max(90ms,beat×0.22), D=max(130ms,duration×0.30). Консервативные границы: previousEnd+O+D < nextStart−O. На44BPM для F4 это2072.73ms <9245.45ms относительно общего anchor, запас около7172.73ms. Это **расчёт геометрии документа**, не измеренная задержка устройства и не работающий новый валидатор. Для beat-boundary профиля длительность имеет другую существующую формулу; политика пересчитывается согласованно, название voicev2 не включает timingPrecisionv2 автоматически.

Если расширенные окна касаются/пересекаются, случай остаётся неподдержанным этой узкой версией. Одновременный одинаковый MIDI в двух линиях, перекрывающиеся удержания/два канала без сохранённой идентичности, ties/подмена пальца на удержании и доказательство педали не добавлены. Внутри линии повтор высоты после rest остаётся отдельным появлением; legato-ребро соединяет разные высоты, а общая высотная очередь не создаёт межголосовую tie.

Окна идентичности не расширяют допуски собственно legato: прежние min(90ms,beat×0.12) gap/min(100ms,beat×0.15) overlap, атаки/длительности/окончания сохраняются. При другом gradingBPM окна проверяются снова; сервер использует BPM выданного плана. Формулы и консервативная область — выбор проекта, не предписание W3C/MIDI Association.

## Совместимость и план проверки

Новое requirement/body/policy условно входят в fingerprint и musicVersion только при наличии, как описано07. Наличие новой версии делает новую музыкальную редакцию; её нельзя зачесть старым результатом. Старые реальные issued-попытки используют saved plan_raw без нового контракта и прежнюю ветку; ранее сохранённые result/digest/XP/progress/goal_key/policy_version не пересчитываются. Само plan_raw не замораживает исполняемый код, поэтому будущая явная диспетчеризация и проверки legacy обязательны. Гипотетическая v1-voice-редакция сохраняет свою строгую область, неизвестная v2 не превращается в legacy. Контракт не меняет catalog7/MusicDocument1/Assessment.VERSION1/pending-storage-v1 и не является XP-мигратором.

В JSON11 перечислены положительные, отрицательные и неподдержанные cases: две правильные F4; перестановка списка voices при том же времени/ID; пропуск каждой F4; длинное удержание/дубликат/лишняя нота; повторное потребление события; неверные ссылки; пересекающиеся/касающиеся окна; одновременный унисон; канальная/педальная неопределённость; старый hash/issued-result/retry/XP. Они плановые, не выполненные. Для нового grade будущие core/service/browser должны потреблять одну сохранённую каноническую версию и одну таблицу сопоставления; документ сам этого не реализует.

## Первичные технические источники

[W3C Web MIDI API](https://www.w3.org/TR/webmidi/), Working Draft31октября2026, Abstract/5.4.1/5.5: MIDIMessageEvent содержит байты и timestamp, API намеренно не задаёт музыкальную семантику. Это draft, не утверждённая рекомендация; он не описывает наши ID, руки, допуски или оценщик. Текущий обработчик использует performance.now при обработке, поэтому его время не объявляется физическим временем клавиши без задержки.

[MIDI Association, Summary of MIDI1.0 Messages](https://midi.org/summary-of-midi-1-0-messages), Table1 Channel Voice/NoteOn/NoteOff/ControlChange: статус несёт канал, данные — номер ноты/velocity; сообщения контроллеров отдельны. Это обзор, не полная спецификация. Наличие MIDI-канала в raw-байтах не означает физическую руку; текущий путь живой попытки его не сохраняет. Добавлена1 запись/применение и1 применение прежнего WebMIDI-источника, реестр63→64. Нового подключения MIDI, permission, устройства, SSO, звуковой/педагогической проверки нет.
