## Что изменить в эксплуатации

1. **Убирать распаковки после успешной проверки**,оставляя immutable архив,manifest,результаты и проверенные current/previous. Сейчас staging сохраняет и сжатый выпуск,и раскрытые исходники/тестовые каталоги,и candidate payload. Например,currentcourse222 содержит около77МиБ в`restored` и59МиБ в`isolated-candidate-payload-v2`;его основной архив —15,77МиБ. Действующий профиль ссылается на архив,поэтому будущему cleaner нужен учёт конкретных файлов,а не удаление родителя целиком.
2. **Ограничить историю local payload и recovery kit после подтверждённого внешнего restore.** Существующий read-only planner уже знает keepNewest3,возраст6часов,защищённые source/current/previous и2 кандидата/64МиБ за план. Эти пределы не повышались;обхода последовательными автоматическими удалениями не было. Получен свежий план с2 полностью проверенными payload,удаление/карантин не выполнялись. Карантин на том же диске сам по себе место не освобождает;финальное удаление требует отдельного подтверждённого шага.
3. **Переиспользовать immutable архив по SHA**,создавая самодостаточный набор только для конкретного copy/restore и очищая его рабочую копию после подтверждения. Архив100 размером13155622B найден в8 отдельных inode сSHA`d4087bb957e778116f216f09b577f84f255f4de3fffd7ed6895d16c47c55d9c3`. Это реальный пример лишних копий;менять формат recovery или подменять файлы ссылками без проверки потребителей нельзя. Всего для этого аудита прочитано110400593B архивов при лимите128МиБ,весь массив архивов не перехешировывался.
4. **Проверять необходимые входные архивы worker в мониторинге наличия/изменения.** Успешная старая freshness-квитанция не доказывает,что файл,на который ссылается профиль,всё ещё существует. Нужен дешёвый контроль path/type/size и SHA при изменении,без ежечасного полного coldrestore. Реализация такого guard — отдельная подготовленная задача;здесь код worker не изменялся.

Само приложение не является главным потребителем:текущая веб-сборка около3,3МиБ,папка PostgreSQL около73МиБ;все сохранённые web releases около127МиБ. Переезд курса на S3/CDN или переписывание интерфейса не решает накопление локальных QA/staging копий. Сжатый исходный артефакт186 —16532547B;при распаковке только `source/tests` занимает40942754B,документы —27726000B,поэтому повторная распаковка для каждого этапа заметно умножает объём. Сжатый sourcecut/история сохраняются;не предлагалось вырезать тесты или редакции из их единственной копии.

## Docker

MelodiaJest использует те же2 образа Nginx/PostgreSQL,что и соседние контейнеры. Новый урок не создаёт отдельный Docker image. Во всём Docker27 образов,14 контейнеров;глобальный build-cache счётчик459/7,117GB(~6,63ГиБ),причёмобычныйDockerсчётчикпоказал0B reclaimableдляcache. Весь этот объём не приписывается MelodiaJest и не добавляется к её резерву. Образы/volumes/общийcache не удалялись.

Общий BuildKit cache следует регулировать отдельно на уровне всего VPS с учётом используемых образами shared данных и политики возраста/размера,а не запускать общий prune ради одной MelodiaJest. Основание: [официальная документация Docker GC](https://docs.docker.com/build/cache/garbage-collection/). Изменений daemon.json/BuildKit/чужих сервисов нет.
